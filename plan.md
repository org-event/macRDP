# macRDP — тезисный план

Основа — `explorer.md`. Цель: работать на удалённом Mac как за своим, целый день. Свои машины, без чужих серверов. В парке есть Intel.

**Решение:** пишем RDP-сервер для macOS. Клиенты берём готовые: Windows App от Microsoft (Mac, Windows, iOS), Remmina/`xfreerdp` (Linux). Свой клиент пишем, только если чужие не дадут нужного качества.

## 1. Почему RDP-сервер

- Mac → Windows через Windows App уже работает хорошо. Если Mac-хост говорит на том же протоколе, клиенты на всех системах получаем бесплатно.
- В macOS нет RDP-сервера. «Общий экран» и Apple Remote Desktop работают по VNC. Shadow-сервер FreeRDP для Mac устарел. Ниша пустая.
- Протокол открыт (MS-RDPBCGR, MS-RDPEGFX и др.). Реверсить нечего.
- Одна серверная часть вместо сервера и клиентов под каждую ОС.

**Важно:** Windows→Windows работает хорошо, потому что сервер Microsoft годами вылизан. Наше качество зависит от нашей серверной части: как захватываем, как кодируем, какие возможности RDP реализуем. Клиент только показывает то, что ему дали.

## 2. Что должно быть в сервере, чтобы было как с Windows

- **Графика через канал GFX (MS-RDPEGFX) с H.264.** Режим AVC420 даёт скорость, AVC444 — резкий текст. AVC444 — это два обычных потока 4:2:0, поэтому он работает на аппаратном кодере любого Mac, включая Intel. Без GFX остаются старые bitmap-обновления, а это уровень VNC.
- **Курсор отдельно** (pointer-сообщения RDP). Клиент рисует его сам, задержка курсора почти нулевая.
- **Клавиатура:** скан-коды RDP → keycode Mac. Клавиша Win → Command. Как Windows App на Mac отправляет Command, нужно проверить: это может быть Win, а может быть Ctrl.
- **Буфер обмена** (CLIPRDR), затем звук (RDPSND), затем диски (RDPDR).
- **Разрешение под клиента** (Display Control): виртуальный дисплей через `CGVirtualDisplay`.

## 3. На чём строить

| Часть | Варианты |
| --- | --- |
| RDP-протокол сервера | **FreeRDP** (C). Серверные библиотеки с GFX и AVC444 проверены в бою: на них построен gnome-remote-desktop, его код — готовый образец. **IronRDP** (Rust) моложе и аккуратнее; есть ли в нём серверный GFX/H.264, надо проверить. |
| Захват | ScreenCaptureKit (macOS 12.3+), `dirtyRects` для обновления только изменённого. |
| Кодирование | VideoToolbox H.264, realtime, без B-кадров. |
| Ввод | `CGEventPost` + Accessibility. Образец — хост Chrome Remote Desktop (Chromium, `remoting/host/mac`). |
| Работа как служба, экран входа | Там же, в Chromium remoting: daemon, login window, права TCC. |
| Доступ снаружи | Свой WireGuard. RDP в интернет напрямую не выставляем. |

Проверено 2026-10-28 по исходникам IronRDP (main): `ironrdp-server` с feature `egfx` отправляет AVC420/AVC444 и принимает уже готовый H.264, то есть можно подать вывод VideoToolbox. Разбор кадра для AVC444 есть в `ironrdp-egfx/src/avc444.rs`. Есть UDP-транспорт (`with_udp_transport`, MS-RDPEUDP2), по нему идёт EGFX. В FreeRDP shadow такого нет — только TCP.

Выбор: **сразу IronRDP (Rust)**: UDP, безопасная память, свой кодер VideoToolbox. Проверка на FreeRDP отменена; черновик модуля (`src/mac_subsystem.m`) остаётся как образец логики ввода и курсора для переноса.

**Где разрабатывать:** на Apple Silicon-хосте. Там же запускается сервер. Intel Mac с Windows App — тестовый клиент.

**Типовой сценарий:** клиент — Windows App на Intel Mac, хост — Apple Silicon. На хосте мощный аппаратный кодер и свежая macOS, поэтому ограничения Intel со стороны хоста (раздел 5) уходят на второй план. Подстраиваемся под возможности одного клиента — Windows App.

**Состояние на 2026-10-28.** Крейт `macrdp` (Rust, IronRDP по зафиксированному коммиту): ScreenCaptureKit → VideoToolbox H.264 → EGFX AVC420, ввод через `CGEventPost`. Проверено: FreeRDP 3.32 (GFX V8.1) и Windows App на Mac (GFX V10.7) — локально и с другого Mac через WireGuard; настоящий захват, клавиатура, мышь, скролл работают. Найдено: FreeRDP требует в ResetGraphics хотя бы один монитор; Windows App рвёт TLS на ECDSA-сертификате — самоподписанный теперь RSA 2048. Права TCC получает приложение, из которого запущен сервер (Terminal, Ghostty), а не сам бинарник. Не проверено: как Windows App передаёт Command/Option.

## 4. Этапы и сроки (1 разработчик)

**Этап 0 — проверка, 3–5 дней**
- Собрать FreeRDP на Mac, поднять минимальный сервер: захват → H.264 → GFX, без ввода.
- Подключиться из Windows App на Mac и на Windows. Оценить резкость текста, задержку, поведение при движении окон.
- Проверить, какие скан-коды приходят от Windows App на Mac при нажатии Command/Option.
- Тот же замер для Remmina на Linux.
- Итог: годятся ли готовые клиенты. Если да — дальше только сервер.

**Этап 1 — рабочий сервер в LAN, ~2 недели**
- Ввод: клавиатура, мышь, скролл. ✅ Раскладка переключается по Ctrl+Space на стороне сервера.
- Курсор отдельным каналом. ✅
- AVC444 для текста.
- Буфер обмена.
- Вход: учётка Mac через NLA/CredSSP или свой пароль сервера (решить).

**Этап 2 — «можно работать день», ~1–2 недели**
- Разрешение под монитор клиента (Display Control + виртуальный дисплей). ✅ С пределом 3072×1920 по площади (`--max-size`); дальше — подстраивать предел по fps клиента.
- Адаптивный битрейт; 60 к/с только при движении, чтобы не грелся Intel.
- Переподключение к той же сессии.

**Этап 3 — эксплуатация, ~1–2 недели**
- LaunchDaemon + агент: работает после перезагрузки и на экране входа.
- Curtain (экран хоста гаснет), звук, диски.
- Доступ снаружи через свой WireGuard.

Итого: годность подхода — за неделю, рабочий сервер — ~3 недели, «весь день» — 5–7 недель.

## 5. Запасной путь: свой клиент

Нужен, если на этапе 0 окажется, что Windows App или Remmina портят качество: мылят текст, плохо держат задержку по TCP или неисправимо ломают Command. Тогда пишем свой клиент поверх того же захвата и кодера. RDP-сервер при этом остаётся входом для всех остальных.

## 6. Ограничения RDP, о которых знать заранее

- По умолчанию TCP: потери в сети дают рывки. В LAN и через WireGuard по проводу это обычно незаметно. UDP-транспорт RDP на стороне сервера в открытых библиотеках, насколько известно, не реализован.
- Мы не контролируем клиента: как он декодирует, есть ли аппаратное ускорение, как переводит клавиши.
- Одна пользовательская сессия: подключаемся к тому же рабочему столу, который на экране хоста (как «Общий экран»). Несколько независимых сессий, как в Windows Server, на macOS не сделать.

## 7. Риски

- Права TCC (запись экрана, Accessibility) при работе как служба и на экране входа — самое хрупкое место.
- Приватный `CGVirtualDisplay` может сломаться в новой macOS. Запасной вариант — масштабирование.
- Сборка и поддержка FreeRDP на macOS как сервера — делают немногие, возможны мелкие поломки.

## 8. Решения, которые нужно принять

1. Точный список моделей Mac и версий macOS (минимум 12.3 на хосте).
2. FreeRDP (C) или IronRDP (Rust) — по итогам этапа 0.
3. Вход: учётная запись Mac или отдельный пароль сервера.
